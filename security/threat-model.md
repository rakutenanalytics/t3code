# Managed build threat model

A leak is disclosure of workspace content, conversation text, attachments, terminal or browser data, credentials, project/thread titles, identifying metadata, or operational logs to an unapproved destination. Cloud tunnels also disclose a reachable control surface, even before content moves.

This build permits direct network access and keeps normal agent/provider use. It denies product analytics, T3 Connect (including saved tunnels, activity publishing and tracing), OTLP export, provider feedback uploads, unmanaged runtime updates, automatic remote chat/PR media and favicon loads, provider metadata probes and supported provider telemetry. Environment variables, CLI flags and saved preferences cannot grant these capabilities.

Desktop auto-update is allowed only in the safe app, pinned to public GitHub releases from `rakutenanalytics/t3code` on `latest`. GitHub release asset redirects use its CDN. Machine policy can disable updates but cannot select another feed. Squirrel verifies each candidate against the installed app's certificate-pinned designated requirement. Existing ad-hoc installs require manual migration to the first signed release.

The boundary is T3-owned feature execution in desktop, web and server/CLI artifacts and source execution. This is not a host firewall, provider sandbox, browser destination filter, or defense against arbitrary code execution. Agent subprocesses, user-selected URLs, provider APIs, SSH, Git hosting and optional installers still need destination approval. A person able to replace the application can replace its policy.

`managed-policy.json` is validated and embedded at build time, including web and desktop development bundles. Without a build define, Node source execution reads `security/managed-policy.json` relative to the shared policy module, independently of the working directory. An absent source file, unavailable source filesystem or baked null selects an empty allow list and denies every modeled capability. Raw nullable helper calls retain permissive upstream semantics; the exported runtime adapter no longer supplies null. Invalid data fails the build or source startup. The embedded policy always wins in compiled artifacts, with null normalized to an empty allow list. Runtime files and environment variables cannot replace it. Source execution uses the repository file, so changing that file changes policy on the next start.

`last-approved-upstream` records the reviewed source anchor and the most recent stable tag it incorporates. The initial anchor includes post-release main changes. `last-approved` retains the original audit SHA for provenance. Static scans and policy smoke are review checks, not runtime network enforcement.

The upstream administrator policy is an additional restriction, not a replacement for the baked policy. Its `telemetry`, `connect`, `clients` and `updates` limits overlap only part of the fork's capabilities. Metadata, provider telemetry, feedback, OTLP and remote-content gates remain necessary. Outbound linked-environment credentials have their own default-closed `peerLinks` gate; allowing inbound remote clients does not authorize outbound peer links.
